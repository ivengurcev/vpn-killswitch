## 2. Доработки уровня P0

### 2.1. Резолв доменов до записи hosts-блока

**Дефект.** Текущая реализация `enable_protection` последовательно вызывает `apply_hosts_block`, затем `resolve_domains`. После записи в `/etc/hosts` строк вида `0.0.0.0 example.com` и `:: example.com` команда `getent`, использующая NSS-цепочку с приоритетом файла `/etc/hosts`, возвращает именно эти адреса. В результате nftables-сеты `blocked_ipv4` и `blocked_ipv6` наполняются адресами `0.0.0.0` и `::`, а реальные IP защищаемых доменов не блокируются. nftables-уровень защиты при `MANAGE_HOSTS=true` фактически выключен.

**Требования.**
- Резолв защищаемых доменов должен выполняться **до** изменения файла `/etc/hosts`.
- Программа должна гарантировать, что в nftables-сеты не попадают адреса `0.0.0.0`, `::`, а также адреса из RFC1918, link-local (`169.254/16`, `fe80::/10`) и `127.0.0.0/8`, `::1` — такие адреса должны отфильтровываться при формировании сетов с записью предупреждения в журнал.
- Если резолв вернул одни лишь служебные/нулевые адреса для домена, такой результат должен расцениваться как ошибка резолва с попыткой использовать кэш.

**Критерий приёмки.** При неактивном VPN с `MANAGE_HOSTS=true` после применения защиты:
- `nft list set inet vpn_lock blocked_ipv4` содержит реальные публичные IP защищаемых доменов;
- `0.0.0.0` и `::` отсутствуют в сетах.

### 2.2. Фильтрация активного VPN-соединения по типу

**Дефект.** Функция `detect_vpn_status` сравнивает только имя соединения, возвращаемое `nmcli -t -f NAME connection show --active`. Если в системе существует профиль NetworkManager с тем же именем, что и целевое VPN-соединение, но другого типа (например, Ethernet или Wi-Fi), Программа ошибочно сочтёт VPN активным и снимет защиту.

**Требования.**
- Запрос к `nmcli` должен включать поле `TYPE`: `nmcli -t -f NAME,TYPE connection show --active`.
- Соединение считается целевым VPN, если совпадает имя **и** тип принадлежит к множеству VPN-типов: `vpn`, `wireguard`. При необходимости множество должно расширяться через конфигурационный параметр `VPN_CONNECTION_TYPES`.
- При нахождении соединения с совпадающим именем, но не-VPN типом, Программа должна записать предупреждение в журнал и считать VPN неактивным.

**Критерий приёмки.**
- При активном Ethernet-соединении с тем же именем, что и целевой VPN, Программа фиксирует статус `inactive` и включает защиту.
- При активном целевом VPN-соединении статус `active`, защита снята.

## 3. Доработки уровня P1

### 3.1. Замена самодельного lock на flock

**Дефект.** Текущий механизм взаимоисключения создаёт каталог `/run/vpn-lock/lock` и снимает его в trap на `EXIT|INT|TERM`. При завершении процесса по `SIGKILL` или OOM-kill каталог остаётся, и последующие запуски Программы не могут получить lock в течение 100 попыток × 0.1 сек, после чего завершаются с ошибкой.

**Требования.**
- Использовать `flock` для взаимоисключения на файле `${RUN_DIR}/lock`. Lock должен сниматься ядром автоматически при завершении процесса по любой причине.
- При невозможности захватить lock в пределах настраиваемого таймаута Программа завершается без действия с записью `INFO` в журнал (см. п. 3.3).

**Критерий приёмки.** После принудительного завершения процесса `vpn-lock` сигналом `SIGKILL` следующий запуск получает lock без ожидания.

### 3.2. Удаление fallback `RUN_DIR=/tmp/vpn-lock`

**Дефект.** При недоступности `/run/vpn-lock` Программа молча использует `/tmp/vpn-lock` для lock-файла, что разрушает взаимоисключение между параллельными вызовами.

**Требования.**
- Fallback на `/tmp` удалить.
- При недоступности `RUN_DIR` Программа должна завершиться с ошибкой и записью `ERROR` в журнал.
- Установщик создаёт `RUN_DIR` при инсталляции; на systemd-системах каталог в `/run` гарантирован тmpfs.

**Критерий приёмки.** Параллельный запуск двух экземпляров Программы при отсутствующем `/run/vpn-lock` приводит к ошибке обоих, а не к параллельной работе.

### 3.3. Уровни лога для штатных ситуаций

**Дефект.** В функции `disable_protection` при активном VPN вызывается `refresh_ip_cache`, который при недоступном DNS логирует `ERROR`, хотя сам disable отрабатывает успешно. Это создаёт ложноположительные ошибки в журнале.

**Требования.**
- Pre-cache-refresh при `disable_protection` должен логировать неудачу резолва уровнем `WARN`, а не `ERROR`.
- Конкуренция за lock (см. п. 3.1) логируется уровнем `INFO` с пояснением «другой экземпляр Программы выполняется».
- Уровни лога должны различать ошибки, нарушающие защиту, от информационных и предупреждающих сообщений.

**Критерий приёмки.** При активном VPN и недоступном DNS повторный вызов `enforce` не порождает записей уровня `ERROR` в журнале.

### 3.4. Защита от событийного шторма NetworkManager

**Дефект.** Диспетчер `90-vpn-lock` запускает `vpn-lock enforce &` на каждое событие. Серия событий `up` → `dhcp4-change` → `connectivity-change` → `dhcp6-change`, типичная при подключении, порождает несколько параллельных процессов, конкурирующих за lock и многократно резолвящих домены.

**Требования.**
- Реализовать дебаунс: если в пределах настраиваемого окна (по умолчанию 2 секунды) уже было поставлено в очередь действие `enforce`, повторное событие не порождает новый процесс.
- Дебаунс реализуется через файл-маркер с mtime либо через объединение событий в один отложенный запуск.
- Дебаунс не должен подавлять события `vpn-up` и `vpn-down` — они применяются немедленно.

**Критерий приёмки.** Burst из пяти NM-событий за 1 секунду приводит к не более чем двум фактическим запускам `enforce`.

## 4. Доработки уровня P2

### 4.1. Поддержка VPN вне NetworkManager

**Назначение.** Расширить применимость Программы на системы, где VPN управляется напрямую (`wg-quick`, `openvpn` без NM, ручные `tun`-интерфейсы).

**Требования.**
- Ввести конфигурационный параметр `VPN_DETECTOR` со значениями: `networkmanager` (по умолчанию), `wireguard`, `interface`, `script`.
- `wireguard`: VPN активен, если `wg show interfaces` содержит интерфейс с именем `VPN_CONNECTION_NAME`.
- `interface`: VPN активен, если в системе присутствует поднятый интерфейс с именем `VPN_CONNECTION_NAME` и состоянием `UP`.
- `script`: путь к пользовательскому скрипту в `VPN_DETECTOR_SCRIPT`, печатающему `active`, `inactive` или `unknown` в stdout. Любой другой вывод трактуется как `unknown` с применением fail-closed.
- Совместимость: при отсутствии параметра `VPN_DETECTOR` поведение идентично текущему.

**Критерий приёмки.** На системе без NetworkManager с поднятым WireGuard-интерфейсом `wg0` и `VPN_DETECTOR=wireguard, VPN_CONNECTION_NAME=wg0` Программа корректно отслеживает статус и реагирует на `wg-quick down wg0` / `wg-quick up wg0`.

### 4.2. Периодический рефреш IP при неактивном VPN

**Назначение.** При длительной работе с неактивным VPN A/AAAA-записи защищаемых доменов могут измениться. Текущая реализация обновляет nft-сет только по событиям; новые IP не попадают в блокировку до следующего события.

**Требования.**
- Установщик должен создавать `vpn-lock.timer` с настраиваемым интервалом (по умолчанию 5 минут).
- При срабатывании таймера и неактивном VPN выполняется резолв и обновление nft-сетов **без** полного пересоздания таблицы (`add element` / `delete element` для дельты).
- При активном VPN срабатывание таймера — no-op.
- Таймер обязан использовать тот же lock, что и `enforce`.

**Критерий приёмки.** При неактивном VPN изменение A-записи защищаемого домена попадает в `blocked_ipv4` в пределах двух интервалов таймера без внешних событий.

### 4.3. CLI-флаг `--manage-hosts` / `--no-manage-hosts` в установщике

**Назначение.** Сейчас параметр `MANAGE_HOSTS` редактируется только вручную в конфигурации.

**Требования.**
- Установщик должен принимать флаги `--manage-hosts` и `--no-manage-hosts`, перезаписывающие соответствующее значение в конфиге.
- При повторной установке без флага сохраняется ранее заданное значение.
- В `--help` добавляется описание флагов.

**Критерий приёмки.** `setup-vpn-lock.sh ... --no-manage-hosts` приводит к `MANAGE_HOSTS="false"` в конечном конфиге.

### 4.4. Команда `vpn-lock test`

**Назначение.** Диагностический режим для проверки актуальности защиты после установки или после изменений конфигурации.

**Требования.**
- Команда выполняет проверки и печатает результат каждого пункта (`OK` / `FAIL` с пояснением):
  - наличие nftables-таблицы и непустых сетов при неактивном VPN;
  - наличие managed-блока в `/etc/hosts` при `MANAGE_HOSTS=true` и неактивном VPN;
  - отсутствие managed-блока и nftables-таблицы при активном VPN;
  - доступность `nmcli`, `nft`, `getent`;
  - корректность конфигурации (вызов `install_check`).
- Опционально: проверка фактической блокировки методом `curl --resolve domain:443:resolved_ip https://domain` и интерпретации кода ответа/ошибки.
- Команда возвращает ненулевой код при наличии хотя бы одного `FAIL`.

**Критерий приёмки.** Команда `vpn-lock test` корректно идентифицирует ситуации: «защита включена и работает», «защита отключена, VPN активен», «дефект защиты» (например, после ручного удаления nft-таблицы при неактивном VPN).

### 4.5. Альтернативный резолвер в обход `/etc/hosts`

**Назначение.** Дополнительная защита от класса проблем с самоотравлением резолва (см. п. 2.1) и обходом NSS.

**Требования.**
- Конфигурационный параметр `RESOLVER` со значениями `getent` (по умолчанию), `dig`, `systemd-resolve`.
- Для `dig` и `systemd-resolve` запросы выполняются напрямую к системным DNS-серверам в обход `/etc/hosts`.
- При отсутствии выбранного резолвера в системе Программа делает fallback на `getent` с записью `WARN`.

**Критерий приёмки.** При `RESOLVER=dig` и записи `0.0.0.0 example.com` в `/etc/hosts` команда `vpn-lock resolve` возвращает реальный IP домена, а не `0.0.0.0`.

## 6. Совместимость

- Доработки не должны нарушать существующий контракт CLI: команды `enforce`, `enable`, `disable`, `status`, `resolve`, `install-check` сохраняют семантику.
- Доработки не должны требовать ручной миграции существующих установок: повторный запуск `setup-vpn-lock.sh` обновляет конфиг, добавляя новые параметры со значениями по умолчанию.
- Деинсталлятор должен корректно обрабатывать как старые, так и обновлённые установки.
